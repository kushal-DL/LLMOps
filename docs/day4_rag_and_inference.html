🚀 Big Picture: RAG Pipeline

Day 4 builds a complete Retrieval-Augmented Generation (RAG) system from scratch. The key architectural insight: instead of baking knowledge into model weights (expensive, stale), keep it in an updatable retrieval index. The LLM reads retrieved facts; it never has to memorise them.

2. Semantic Embeddings + FAISS Index

Classical keyword search (BM25, TF-IDF) fails on paraphrases — "motorised chair battery" won't match "WCBD dry cell." Sentence embeddings map text into a high-dimensional space where semantic similarity equals geometric proximity.

# Load embedding model (22M params, 384-dim output)
embedder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device=device)

FAISS IndexFlatIP

IndexFlatIP is an exact brute-force index using inner product (dot product). After L2 normalisation, inner product equals cosine similarity. For 40 documents, brute-force is fast enough — at millions of docs, you'd use IndexIVFFlat (inverted file) or IndexHNSW (approximate nearest neighbours).

Why L2-normalise? Raw embedding vectors have varying magnitudes. A long document naturally has a larger dot product with any query, even if it's semantically unrelated. L2 normalisation (dividing by the vector's length) converts dot product into cosine similarity — a magnitude-independent measure of directional agreement between [0, 1].

3. Retrieval

Given a query, we embed it, normalise, and search FAISS for the top-k nearest document vectors. Cosine similarity of 1.0 means identical meaning; 0.0 means orthogonal (unrelated); negative means opposite.

def retrieve(query: str, k: int = 3) -> list[tuple[str, float]]:
    # 1. Embed and normalise the query
    query_emb = embedder.encode([query], normalize_embeddings=True).astype(np.float32)
    # 2. FAISS inner-product search (= cosine similarity after normalisation)
    scores, indices = index.search(query_emb, k)
    # 3. Return (passage_text, similarity_score) pairs
    return [(documents[idx], float(scores[0][rank]))
            for rank, idx in enumerate(indices[0])]

Cosine Similarity: How the Retriever Scores Passages

After L2-normalisation, inner product = cosine similarity. The query vector is compared to every document vector; the angle between them determines the score.

1.00
Identical Meaning
Query and passage point in exactly the same direction (0° angle)
0.75
Highly Relevant
Strong semantic overlap; typically retrieved in top-1 or top-2
0.10
Unrelated
Near-orthogonal vectors; query and passage about different topics
Why not Euclidean distance? L2 distance penalises magnitude differences. Two passages that say the same thing in different lengths would score differently. Cosine similarity is purely directional — magnitude-invariant.
Paraphrase retrieval in action The query "motorised wheelchair with a lithium battery" has no exact keyword overlap with "WCBD dry cell battery-powered mobility device" — but both embed near each other in the 384-dimensional semantic space. BM25 would score this pair near zero; cosine similarity scores it >0.80.

4. Augmented Generation

The RAG pipeline has three stages. The retrieved passages become part of the prompt, giving the LLM explicit facts to read rather than relying on memorised weights.

Three-stage RAG loop 1. Retrieve → top-k passages from FAISS    2. Augment → prepend passages as context in the prompt    3. Generate → LLM reads the context and produces an answer 
print("Loading generation model (GPT-2)...")
gen_tokenizer = AutoTokenizer.from_pretrained("gpt2")
gen_model = AutoModelForCausalLM.from_pretrained(
    "gpt2", torch_dtype=torch.float16
).to(device)
gen_tokenizer.pad_token = gen_tokenizer.eos_token

def rag_generate(question: str, k: int = 3, max_new_tokens: int = 120) -> dict:
    # 1. Retrieve
    retrieved = retrieve(question, k=k)
    context = "\n\n".join([f"[{i+1}] {p}" for i, (p, _) in enumerate(retrieved)])

    # 2. Augment
    prompt = (
        f"Travel industry knowledge:\n{context}\n\n"
        f"Question: {question}\n"
        f"Answer based on the above context:"
    )

    # 3. Generate
    inputs = gen_tokenizer(prompt, return_tensors="pt",
                            truncation=True, max_length=900).to(device)
    prompt_len = inputs["input_ids"].shape[1]

    with torch.no_grad():
        output_ids = gen_model.generate(
            **inputs, max_new_tokens=max_new_tokens,
            do_sample=True, temperature=0.7, top_k=50,
            repetition_penalty=1.2,
            pad_token_id=gen_tokenizer.eos_token_id,
        )

    answer = gen_tokenizer.decode(output_ids[0][prompt_len:], skip_special_tokens=True)
    return {"question": question, "prompt_tokens": prompt_len, "answer": answer.strip()}

GPT-2 is a completion model (not instruction-tuned), so outputs are fluent continuations — not Q&A-style answers. In production, swap in Gemma-2-2b with the travel-expert LoRA from Day 3.

Why does output_ids[0][prompt_len:] extract only the answer? Autoregressive models return the full sequence (prompt + generated tokens). Slicing from prompt_len onward strips the context and question, leaving only the new generated content. Without this, you'd print the entire 900-token prompt before the 120-token answer.

5. Retrieval Evaluation — MRR and nDCG

To know whether retrieval is good, we need labelled relevance: for each query, which passages should be retrieved? We create 5 queries with known-relevant passage indices and evaluate our retriever on two metrics.

MetricFull nameWhat it measuresRange
MRRMean Reciprocal RankHow early does the first relevant passage appear? 1/rank of first hit.0–1
nDCG@kNormalised Discounted Cumulative GainGraded relevance: top positions matter more than lower positions. Perfect ranking = 1.0.0–1
def reciprocal_rank(retrieved_indices, relevant_indices):
    for rank, idx in enumerate(retrieved_indices, start=1):
        if idx in relevant_indices:
            return 1.0 / rank
    return 0.0   # no relevant passage found

def ndcg_at_k(retrieved_indices, relevant_indices, k=5):
    import math
    dcg = sum(
        1.0 / math.log2(rank + 1)       # positions at rank 1,2,3... contribute less
        for rank, idx in enumerate(retrieved_indices[:k], start=1)
        if idx in relevant_indices
    )
    # Ideal DCG: all relevant docs at rank 1,2,3...
    ideal = sum(1.0 / math.log2(r + 1)
                for r in range(1, min(len(relevant_indices), k) + 1))
    return dcg / ideal if ideal > 0 else 0.0

nDCG vs MRR MRR only cares about the first relevant result. nDCG grades all positions — finding a second relevant document at rank 3 is better than finding it at rank 5. For RAG where you retrieve k=3–5 passages, nDCG is a more complete quality signal.

6. KV Cache Benchmark

During autoregressive generation, each new token attends to all previous tokens. Without caching, every forward pass recomputes Keys and Values for the entire sequence — O(n²) per token. The KV cache stores these tensors so only the new token needs computation.

KV Cache: What Gets Recomputed?
Without Cache — O(n²)
Token 1: compute K,V for [t0]
Token 2: recompute K,V for [t0, t1]
Token 3: recompute K,V for [t0, t1, t2]
Token n: recompute K,V for all n tokens ...
With Cache — O(n)
Token 1: compute & store K,V for [t0]
Token 2: append K,V for t1 → use cache
Token 3: append K,V for t2 → use cache
Token n: one new projection, no recompute
# Long prompt to make the cache difference measurable
long_context = "\n".join([d[:200] for d in documents[:5]])
prompt = f"Context:\n{long_context}\n\nSummarise the key takeaways:"
inputs = gen_tokenizer(prompt, return_tensors="pt",
                        truncation=True, max_length=800).to(device)

N_RUNS = 3
MAX_NEW = 80

# Without KV cache
times_no_cache = []
for _ in range(N_RUNS):
    t0 = time.perf_counter()
    with torch.no_grad():
        gen_model.generate(**inputs, max_new_tokens=MAX_NEW,
                            do_sample=False, use_cache=False)
    times_no_cache.append(time.perf_counter() - t0)

# With KV cache (default)
times_cache = []
for _ in range(N_RUNS):
    t0 = time.perf_counter()
    with torch.no_grad():
        gen_model.generate(**inputs, max_new_tokens=MAX_NEW,
                            do_sample=False, use_cache=True)
    times_cache.append(time.perf_counter() - t0)

t_no, t_yes = np.mean(times_no_cache), np.mean(times_cache)
speedup = t_no / t_yes

KV cache memory cost The cache stores K and V tensors for every layer and every token. For GPT-2 (12 layers, 64 heads, 64-dim each): 2 × 12 × n_tokens × 64 × 4 bytes. For 800 tokens that's ~4.7 MB — trivial. At 32k tokens with a large model (Llama-3-70B), KV cache can reach 40+ GB — driving demand for techniques like GQA (Day 2), PagedAttention (vLLM), and quantised KV caches.

7. Batched Inference

Running one request at a time leaves GPU utilisation at 10–20% because matrix multiplications are not saturating the hardware. Batching multiple sequences lets the GPU parallelise operations across requests.

batch_questions = [
    "What are the mandatory PNR fields?",
    "Explain WCHR vs WCBD SSR codes.",
    "How does KV cache improve inference speed?",
    "What does inventory nesting mean for fare pricing?",
    "When does a ghost segment block ticket issuance?",
    "How is baggage compensation calculated under Montreal Convention?",
    "What is the difference between active and passive GDS segments?",
    "How does point-of-sale logic affect fare pricing?",
]
MAX_NEW_BATCH = 60

# Sequential: one request at a time
t0 = time.perf_counter()
for q in batch_questions:
    inp = gen_tokenizer(q, return_tensors="pt").to(device)
    with torch.no_grad():
        gen_model.generate(**inp, max_new_tokens=MAX_NEW_BATCH, do_sample=False,
                            pad_token_id=gen_tokenizer.eos_token_id)
seq_time = time.perf_counter() - t0

# Batched: all 8 requests in one forward pass
gen_tokenizer.padding_side = "left"   # Left-pad for GPT-style models
batch_inputs = gen_tokenizer(
    batch_questions, return_tensors="pt",
    padding=True, truncation=True, max_length=200
).to(device)
t0 = time.perf_counter()
with torch.no_grad():
    gen_model.generate(**batch_inputs, max_new_tokens=MAX_NEW_BATCH, do_sample=False,
                        pad_token_id=gen_tokenizer.eos_token_id)
batch_time = time.perf_counter() - t0

Left-padding for GPT-2 batching GPT-2 is a decoder-only model that processes tokens left-to-right. When batching sequences of different lengths, padding must go on the left so all sequences end at the same position — the model generates from the right edge. Encoder models (BERT) pad on the right. Forgetting this for GPT-style models produces garbage outputs for shorter sequences in the batch.

Key Concepts Mastered

  • RAG vs fine-tuning: RAG for updatable knowledge; fine-tuning for style/domain adaptation
  • Semantic embeddings: 384-d vectors where angle encodes meaning, not keywords
  • FAISS IndexFlatIP: Exact cosine search; swap for IVF/HNSW at million-doc scale
  • L2 normalisation: Converts dot product to cosine similarity — magnitude-invariant
  • MRR: First-hit quality; nDCG@k: graded quality across all k positions
