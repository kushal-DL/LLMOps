🚀 Big Picture: Full Fine-Tuning Pipeline

Day 3 takes you from a raw pre-trained base model all the way to a 1.6 GB quantised file running on your laptop. The key insight: you never touch the 2.6B base-model weights. Instead, LoRA adds thin trainable layers on top, and the whole pipeline is modular — adapters can be swapped onto any copy of the base model.

Why LoRA? Fine-tuning all 2.6B parameters needs ~40 GB VRAM and hours of compute. LoRA (Low-Rank Adaptation) inserts small trainable matrices alongside frozen weights, training only ~13 M parameters — 0.5% of the total — in minutes on a free T4 GPU.
LoRA: Low-Rank Matrix Decomposition

Each weight matrix W0 (frozen) gets two tiny trainable companions B and A. Only B and A receive gradient updates. At inference, their product is added to W0:

Wadapted = W0 + ΔW = W0 + B · A
B ∈ ℝd × r,   A ∈ ℝr × k,   r « min(d, k)   →   r = 16 in this notebook
W0 (frozen, d×k)
+
B (d×r, trainable)
·
A (r×k, trainable)

3. Training Dataset — Travel Industry Q&A

The notebook uses the Alpaca instruction-tuning format: each example has an instruction, optional input context, and the desired output. This is the same format used to fine-tune Llama, Mistral, and many production models.

Domain: Global Distribution Systems (GDS) The dataset covers airline booking systems — the complex middleware that travel agents use worldwide. This is deliberately a narrow, technical domain where a general-purpose LLM underperforms.
Topic clusterWhat the model learns
PNR structureThe 5 mandatory fields (PRINT mnemonic); orphan-record debugging
SSR / OSI codesSpecial service requests — wheelchair types (WCHR/WCBD), battery regulations
Cryptic commandsAmadeus/Sabre shorthand vs GUI equivalents; log-level debugging
RegulatoryDOT Part 382, accessibility requirements, cross-system sync failures

raw_data = [
 {
  "instruction": "Explain PNR Structure to a junior agent.",
  "input": "A trainee is struggling to remember the mandatory fields.",
  "output": "Think of a PNR as the 'Identity Document' of a trip. To make it official ..."
 },
 ...
]

# Format as instruction/response prompt
def format_example(ex):
    if ex["input"]:
        return f"### Instruction:\n{ex['instruction']}\n\n### Input:\n{ex['input']}\n\n### Response:\n{ex['output']}"
    return f"### Instruction:\n{ex['instruction']}\n\n### Response:\n{ex['output']}"

texts = [format_example(ex) for ex in raw_data]
train_ds = Dataset.from_dict({"text": texts})
Dataset Topic Clusters
📄 PNR Structure PRINT mnemonic — Phone, Received, Itinerary, Name, Ticketing. Missing any one = orphan record.
✈ SSR / OSI Codes WCHR (wheelchair ramp) vs WCBD (battery-dry cell). Critical for airline cargo hold regulations.
💻 Cryptic Commands Amadeus/Sabre shorthand. E.g. RT JSMITH/JOHN → Retrieve booking for John Smith.
📚 Regulatory DOT Part 382 wheelchair passenger rights. Profile-to-PNR sync failure patterns.
Each example targets a specific persona (junior agent, data engineer, traveller) — teaching the model to adapt explanation depth.
Why so few examples? LoRA fine-tuning is sample-efficient because the base model (trained on 2T tokens) already knows how to write and reason. You're teaching it a narrow style and vocabulary, not learning from scratch. Even 10–50 high-quality examples can meaningfully shift domain performance.

4. Load Base Model + Apply LoRA Adapters

Gemma-2-2b Architecture

Gemma 2 is Google's open-weight model family. The 2B variant has 26 transformer blocks, 2048 hidden dim, 8 KV heads (GQA), trained on 2T tokens. It fits in ~6 GB VRAM in FP16.

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model

model_name = "google/gemma-2-2b"

# 1. Load Tokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token
tokenizer.padding_side = "right"

# 2. Load base model in FP16
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    device_map="auto",
    torch_dtype=torch.float16,
)

# 3. Apply LoRA adapters
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj","k_proj","v_proj","o_proj",
                    "gate_proj","up_proj","down_proj"],
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# trainable params: 13,107,200 || all params: 2,627,198,976 || trainable%: 0.4990

LoRA Target Modules

We apply adapters to all 7 projection matrices per block. Targeting all 7 (not just Q/V) recovers more performance for domain-specific tasks because the FFN and output projections also need domain adaptation.

ModuleRoleWhy LoRA it?
q_proj, k_proj, v_projQuery, Key, Value attentionControls what information is attended to
o_projOutput after attentionProjects attended values back to hidden dim
gate_proj, up_proj, down_projSwiGLU feed-forwardStores domain-specific facts and style

Key LoRA Hyperparameters

ParameterValueMeaning
r16Rank of the low-rank matrices — higher = more expressivity, more parameters
lora_alpha32Scaling factor: effective scale = alpha/r = 2×
lora_dropout0.05Light regularisation on adapter weights only
Why can we use a high LR with LoRA? The adapter matrices start at zero effective perturbation (B is zeroed, A is random Gaussian). The frozen base model is never destabilised — only the small adapters move. This stability allows LRs of 2e-4, much higher than the 1e-5 typical for full fine-tuning.

5. Tokenize the Dataset

The tokenizer converts the Alpaca-format text strings into integer token ID sequences that the model can process. The key design choices here are memory-driven.

def tokenize(batch):
    return tokenizer(
        batch["text"],
        padding=False,        # Pad dynamically per batch, not globally
        truncation=True,
        max_length=1024,      # Cap to fit in GPU memory
    )

tokenized_ds = train_ds.map(tokenize, batched=True, remove_columns=train_ds.column_names)

# Labels = input_ids (causal LM: predict next token at every position)
tokenized_ds = tokenized_ds.map(
    lambda x: {"labels": x["input_ids"]},
    batched=True
)
ChoiceReasoning
padding=FalsePadding is deferred to the DataCollatorForSeq2Seq inside Trainer, which pads to the longest sequence in each batch (not globally). This saves significant VRAM because most batches are shorter than the max.
truncation=True, max_length=1024Gemma-2-2b has a 8192-token context window, but long sequences don't fit with batch_size=1 + FP16 + optimizer state. 1024 is the sweet spot for T4 VRAM.
labels = input_idsFor causal language modelling, the loss is computed over every position — the model predicts token[i+1] from token[0..i]. The Trainer handles the +1 shift internally.
Causal LM Training Signal Unlike masked LM (BERT), causal models learn from every token in the sequence. Given the training text "### Response:\nThink of a PNR as...", the model learns both the format tokens (###, Response) and the actual answer content simultaneously.

6. Training

HuggingFace Trainer abstracts the full training loop: forward pass, backward pass, gradient accumulation, optimizer step, and mixed-precision scaling. All hyperparameters are declared in TrainingArguments.

from transformers import TrainingArguments, Trainer

training_args = TrainingArguments(
    output_dir="./finetune_out",
    per_device_train_batch_size=1,   # 2B model in FP16 leaves little VRAM headroom
    gradient_accumulation_steps=4,   # Effective batch size = 1 * 4 = 4
    warmup_steps=10,
    max_steps=100,                   # ~5 min on T4; use 500+ for production quality
    learning_rate=2e-4,
    fp16=True,                       # Mixed precision
    optim="adamw_torch_fused",       # Fused CUDA kernel ~20% faster than standard AdamW
    logging_steps=10,
    report_to="none",
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_ds,
    processing_class=tokenizer,
)
trainer.train()

Hyperparameter Table

SettingValueWhy

fp16TrueMixed precision — faster matmuls, less memory

Learning Rate Schedule (warmup + constant)
Warmup (steps 0-10)

Gradient Accumulation

With gradient_accumulation_steps=4, the optimizer step only fires every 4 forward+backward passes. Intermediate gradients are accumulated (summed) without zeroing. This simulates a larger batch size without allocating the extra activations — the VRAM cost is identical to a batch size of 1.

adamw_torch_fused vs standard AdamW The fused kernel combines the parameter update, momentum update, and weight decay into a single CUDA kernel launch instead of three separate ones. This reduces kernel launch overhead and memory round-trips by ~20%. For LoRA with only 13M trainable parameters, the speedup is modest but free.

7. Save Adapters & Test Inference

model.save_pretrained() saves only the LoRA adapter weights and config — roughly 50–100 MB — not the 6 GB base model. Anyone with the base model can reconstruct the fine-tuned variant by loading the adapter on top.

# 1. Save adapters only (~50-100 MB, not the 6 GB base)
model.save_pretrained("./my_custom_model")
tokenizer.save_pretrained("./my_custom_model")

# 2. Complex multi-persona inference test
scenario_instruction = """Explain the situation below to a Junior Agent and a Data Engineer.
Context: A traveler with a motorized wheelchair (WCBD - dry cell) is flying US to Japan.
The airline's DCS is rejecting the PNR because the SSR code was entered as WCHR instead
of WCBD.
Please cover:
1. The Technical mismatch between WCHR and WCBD.
2. The Regulatory aspect citing DOT Part 382.
3. The Data challenge of why the Profile-to-PNR sync failed."""

prompt = f"### Instruction:\n{scenario_instruction}\n\n### Response:\n"
inp = tokenizer(prompt, return_tensors="pt").to("cuda")

out = model.generate(
    **inp,
    max_new_tokens=512,
    temperature=0.7,
    do_sample=True,
    repetition_penalty=1.15,
    eos_token_id=tokenizer.eos_token_id,
    pad_token_id=tokenizer.pad_token_id,
)
decoded = tokenizer.decode(out[0], skip_special_tokens=True)
response = decoded.split("### Response:\n")[-1].strip()
print(response)
Why this specific test scenario? The scenario deliberately crosses three training domains simultaneously — SSR code mismatch (technical), DOT Part 382 (regulatory), and Profile-to-PNR sync failure (data engineering). A model that only memorised individual examples would fail; a model that generalised can synthesise an answer that bridges all three.

Inference Parameters Explained

ParameterValueEffect
temperature=0.7—Adds creativity while staying professional. 1.0 = random; 0.0 = greedy.
do_sample=True—Enables stochastic sampling (temperature only works if sampling is on)
repetition_penalty=1.15—Penalises already-generated tokens — stops "### Response: ### Response:" looping
max_new_tokens=512—Sweet spot: enough for a detailed multi-part answer, not so long it wanders

10. Merge Adapters into Base Model

merge_and_unload() fuses the adapter matrices back into the base weights permanently. This is a prerequisite for GGUF export because llama.cpp's conversion script expects a plain HuggingFace model directory — it doesn't understand PEFT adapter files.

merged_model = model.merge_and_unload()
merged_model.save_pretrained("./merged_model_for_ollama")

11. Export to GGUF (llama.cpp Format)

GGUF is the binary format used by llama.cpp, Ollama, LM Studio, and most local inference runtimes. It bundles the model weights, tokenizer, and all metadata into a single file.

The conversion script needs the binary. Fix: download it explicitly with an authenticated HF token and place it alongside the merged model weights.

12. Quantise to Q4_K_M

Quantisation maps FP16 weights (2 bytes each) to 4-bit integers (0.5 bytes), reducing model size by ~4× with modest quality loss. K-Quant uses k-means clustering per block — centroids are chosen to minimise reconstruction error, giving better quality than naive INT4.

# Build llama-quantize
!cd llama.cpp/build && cmake --build . --config Release --target llama-quantize

# Quantize FP16 to Q4_K_M
!./llama.cpp/build/bin/llama-quantize \
    travel_expert_fp16.gguf \
    travel_expert_q4.gguf \
    q4_k_m

PPL = perplexity increase vs FP16. Lower = better. Q4_K_M is the sweet spot for most laptops and Ollama deployments.

FormatSizePPL vs FP16Use case
FP16~5 GBbaselineCloud inference / GPU servers
Q8_0~2.7 GB+0.05High-VRAM laptops (RTX 3080+)
Q4_K_M~1.6 GB+0.3Most laptops / Ollama (recommended)
Q3_K_S~1.2 GB+0.7Memory-constrained / older hardware
K-Quant vs Naive INT4 Standard INT4 maps each weight to the nearest 4-bit integer on a fixed uniform grid. K-Quant groups weights into blocks, runs k-means to find the 16 best representative values (centroids), and assigns each weight the nearest centroid. This non-uniform grid dramatically reduces reconstruction error at the same bit width.
